# Ступень 3. Накопительное ТЗ в OpenSpec

Эта личная ветка продолжает результат первых двух ступеней в одном репозитории. Повторное клонирование и импорт не нужны. Подготовлены документы, а не приложение; код калькулятора не добавляется, Apply не запускается.

## Что читать

1. [Предложение](openspec/changes/add-reset-and-years-term/proposal.md): цель и границы изменения.
2. [Спецификация](openspec/changes/add-reset-and-years-term/specs/credit-calculator/spec.md): накопленные требования, сброс и срок в месяцах/годах.
3. [Проектные решения](openspec/changes/add-reset-and-years-term/design.md): подход к будущей реализации.
4. [Задачи](openspec/changes/add-reset-and-years-term/tasks.md): незавершённые шаги будущей реализации с проверками.
5. [Таблица переноса](openspec/changes/add-reset-and-years-term/traceability.md): соответствие всех восьми исходных сценариев новому ТЗ.

Рабочий источник требований — спецификация активного Change `add-reset-and-years-term`. Старый `specification.md` удалён после проверки переноса, но сохранён в истории Git. Пустой `openspec/specs/` не означает потерю требований: Change ещё не архивирован, его требования не объявлены реализованными.

## Проверка документов

В корне этой же папки, где установлен OpenSpec CLI:

```bash
openspec status --change add-reset-and-years-term
openspec validate add-reset-and-years-term --strict
git diff --check
git status --short
```

Ожидаются четыре готовых планирующих артефакта, успешная строгая проверка и отсутствие ошибок форматирования. Готовность артефактов не означает выполнение задач реализации: все 12 задач остаются `[ ]`. Если команда недоступна или завершилась с ошибкой, проверка не пройдена. Для содержательной проверки прочитайте все документы и таблицу переноса; CLI её не заменяет.

## Передача на ревью

Рабочая ветка: `course/example/stage-3-reset-years`. База PR: `course/example/stage-2-reset`. Общая `main` остаётся эталоном и не является целью учебного PR.

После проверки diff сохраните документы и отправьте рабочую ветку. В PR укажите SHA R2, таблицу переноса и фактически выполненные проверки. Другой аналитик проверяет полноту требований, разработчик или архитектор — план и критерии будущих тестов. ИИ-проверка не заменяет эти два человеческих ревью. Ссылку на связанную учебную Jira-задачу добавляйте только после подтверждения её точного ключа.

Для вспомогательной проверки доступно [сообщение для OpenCode](ai/request.md). Текущий пакет подготовлен с помощью ИИ по просьбе пользователя при проверке гайда; самостоятельное ручное выполнение не подтверждено.

Следующее дополнение 3-ИИ должно создать отдельное небольшое изменение через OpenSpec с ИИ на основе этого результата. Требование для него выбирается отдельно; не смешивайте его с текущим Change. Реализация приложения и Apply в эти аналитические упражнения не входят.
