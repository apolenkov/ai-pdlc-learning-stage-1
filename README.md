# Ступень 1. Спецификация в Git

Это вход в основной маршрут обучения: **Введение → R1 → R2 → SDD и OpenSpec → R4**. R3 — факультативное углубление, а не обязательный переход. R1–R3 разбирают один запрос; Git сохраняет его документ и историю между шагами.

Мы переносим договорённости из разрозненных страниц в Git, чтобы у людей и ИИ был один актуальный источник вместо догадок и старых копий. ИИ не всегда знает последние решения команды; рядом с требованиями можно хранить документацию, схемы устройства продукта и код. Позже метарепозиторий свяжет их, а история Git покажет, кто и почему менял договорённость. Отдельный запрос для R4 показывает, как к уже описанному продукту добавляется новая потребность.

Результат R1: собственный документ `intents/clear-calculation-result.md`, уточнённая `specification.md` в личной ветке `course/your_login/stage-1-error-result` и ссылка на ветку в личной учебной задаче Jira. Документ объясняет проблему и желаемый результат; спецификация описывает точные правила и сценарии. Нужны VS Code, Git и корпоративная Jira. Node.js, OpenSpec и код калькулятора на R1 не нужны.

## Сначала сформулируйте запрос

Прочитайте [исходное обращение и ответы](request-and-answers.md) — это источник фактов упражнения. По [общему шаблону замысла](intent-template.md) составьте свой рабочий документ `intents/clear-calculation-result.md`, затем сравните его с [предоставленным примером](examples/clear-calculation-result.md). Папка `examples/` показывает один способ разбора, но не задаёт факты и не заменяет ваш документ. В рабочей ветке файл из `intents/` — единственный актуальный замысел для R1, R2 и факультативной R3; меняйте его вместе с уточнением потребности, а Git сохранит историю. В реальной работе смысл подтверждают инициатор и владелец решения; учебный пример такого согласования не заменяет.

## Где работать и какие права нужны

Откройте [общий учебный эталон](https://github.com/apolenkov/sdd-guide-credit-calculator-stage-1), нажмите **Fork** и выберите своё личное пространство. Скопируйте HTTPS-адрес вашего fork — здесь и во всех примерах ниже `your_login` заменяйте своим логином GitLab:

```text
https://gitlab.example.invalid/your_login/sdd-guide-credit-calculator-stage-1.git
```

В VS Code выполните **Git: Clone** через палитру команд или кнопку **Clone Repository**, вставьте адрес fork, выберите родительскую папку и откройте клонированный корень `sdd-guide-credit-calculator-stage-1`. Эта папка останется рабочей на R1–R3.

После клонирования `origin` уже указывает на ваш fork, поэтому второй remote добавлять не нужно. Не отправляйте решение в `main` и не обходите её защиту. Для R2, R3 и R4 курс требует три отметки по текущему diff: руководителя проекта, аналитика и технического руководителя; при затрагивании архитектуры или споре добавляется четвёртая отметка архитектора. Автоматическая проверка и ИИ не заменяют людей.

Для повторного прохождения добавьте ко всем веткам одинаковый суффикс, например `-2`.

## Задание R1

1. Проверьте папку и создайте личную ветку в VS Code: щёлкните имя текущей ветки в левом конце строки состояния, выберите **Create new branch** и введите `course/your_login/stage-1-error-result`.

   Если панель **Source Control** показывает чужие или неожиданные правки, остановитесь и уточните папку у организатора. Ничего не сбрасывайте.

2. Откройте и прочитайте [исходную спецификацию](specification.md) в VS Code. Внесите решение точно в три места:

   - в подраздел «ПРАВИЛА» добавьте правило: при ошибочном вводе предыдущий результат очищается до «—», а сообщение указывает ошибочное поле;
   - в таблицу подраздела «СЦЕНАРИИ» добавьте сценарий: сначала `120 000 ₽`, `0%`, `12 месяцев` → `10 000 ₽`; затем срок `1,5 месяца` → ошибка у поля срока и «—» вместо результата;
   - в разделе «Открытые вопросы» удалите решённый вопрос и оставьте: «Для данного упражнения открытых вопросов нет».

   Это заданное решение упражнения, а не правило, которое нужно угадать. Четыре исходных сценария должны сохраниться: после правки в документе должно быть ровно пять сценариев.

3. Проверьте и сохраните замысел вместе со спецификацией через панель **Source Control** в VS Code:

   - откройте `intents/clear-calculation-result.md` и `specification.md` в списке **Changes** и прочитайте оба diff;
   - нажмите **Stage Changes** у этих двух файлов и проверьте staged diff ещё раз;
   - введите сообщение `docs: clarify result after invalid input` и нажмите **Commit**.

   После коммита список **Changes** снова пуст. Чтение diff не доказывает работу приложения или человеческое одобрение. Полный SHA коммита можно посмотреть командой `git rev-parse HEAD`, но для R1 это необязательная продвинутая фиксация, а не условие приёмки.

4. Опубликуйте личную ветку в свой fork: в **Source Control** нажмите **Publish Branch** — VS Code отправит `course/your_login/stage-1-error-result` в `origin` и начнёт отслеживать её. Ветка должна появиться в вашем fork в GitLab.

   Личная учебная задача в Jira — обязательный шаг R1: откройте выданную вам Task проекта DEMO или создайте её на себя по шагу «Создайте свою личную задачу в Jira» [канонической инструкции ступени 1](https://apolenkov.github.io/customdev-learning/guides/stage-1.html); порядок доступа к Jira и родитель описаны там и в [корпоративных ресурсах курса](https://apolenkov.github.io/customdev-learning/corporate-resources.html#jira) и здесь не повторяются. Добавьте в задачу ссылку на ветку и краткое решение; полный SHA можно приложить как точную фиксацию, но он необязателен. Не придумывайте ключ, родителя или факт согласования.

Необязательная помощь на R1 описана в [готовом сообщении для корпоративного агента](ai/request.md): маршрут курса — Kilo в VS Code, именованная альтернатива — OpenCode. Она не меняет требования к итоговому diff и личному решению.

## Переход в R2 на следующей ветке

Откройте [полную инструкцию R2](https://apolenkov.github.io/customdev-learning/guides/stage-2.html). Её основной режим продолжает текущий checkout: не выполняйте команды отдельного старта из репозитория `sdd-guide-credit-calculator-stage-2`.

Короткий контракт перехода:

1. Убедитесь, что в VS Code открыт тот же репозиторий с принятой R1: текущая ветка — `course/your_login/stage-1-error-result`, а панель **Source Control** не показывает незакоммиченных правок.
2. От этой ветки создайте `course/your_login/stage-2-reset` — имя ветки в строке состояния → **Create new branch**.
3. В `specification.md` сохраните пять сценариев R1 и добавьте правило сброса плюс три сценария: после успешного расчёта, после ошибки и повторный сброс. Повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибок.
4. Прочитайте diff в **Source Control**, сделайте коммит, опубликуйте ветку и откройте MR со source `course/your_login/stage-2-reset` и target `course/your_login/stage-1-error-result`.
5. Для текущего diff курса нужны отметки руководителя проекта, аналитика и технического руководителя; если изменение затрагивает архитектуру или есть спор, нужна четвёртая отметка архитектора. После содержательной правки отметки обновляют для новой версии.

ИИ и автоматическая проверка не заменяют человеческие отметки. При разрешённом техническом walkthrough без отзывов отмечайте приёмку как незавершённую.

## Факультативное углубление R3

После R2 основной маршрут продолжает обязательная [практика SDD и OpenSpec](https://apolenkov.github.io/customdev-learning/guides/sdd-openspec.html). Затем можно пройти факультативную [R3](https://apolenkov.github.io/customdev-learning/guides/stage-3.html) как ручное углубление перед R4. Она полезна для работы без модели, но не заменяет SDD и R4 в полном курсе. Не клонируйте сервисный пример и не добавляйте приложение ради этой ступени.

R3 создаётся веткой `course/your_login/stage-3-reset-years` от принятой R2. До инициализации обновите `AGENTS.md` под правила R3. Точную разовую инициализацию OpenSpec под Kilo выполняйте в этом же checkout по полной инструкции R3: она вызывает `openspec init --tools none`; последовательность команд здесь не дублируется. Три навыка планирования лежат в репозитории в актуальном layout Kilo — `.kilocode/skills` (`openspec-explore`, `openspec-propose`, `openspec-update-change`), плюс команды `.kilo/command` (`opsx-explore`, `opsx-propose`, `opsx-update`) — и переходят с принятыми ветками R1–R3: Kilo в VS Code находит их сам, генерировать или копировать их не нужно. Полный `openspec init --tools kilocode` не запускайте: он развернёт все рабочие процессы, а ступени R1–R3 ограничены планированием.

Далее запрашивайте `status` и `instructions` для следующего документа планирования и заполняйте его сами. Переносите все восемь сценариев R2 поэтапно. Удаляйте рабочую `specification.md` только после таблицы соответствия и строгой проверки полного Change; в таблице запишите репозиторий, принятый MR R2 и личную ветку — точный коммит при необходимости выводится из проверенного MR, а полный SHA остаётся необязательной продвинутой фиксацией. В этом учебном репозитории нет доказанного рабочего состояния: новые функции остаются в активном Change с незавершёнными задачами. Apply запрещён. Если CLI недоступна, init завершился ошибкой или root оказался другим, остановитесь и следуйте разделу устранения ошибки полной инструкции; не создавайте структуру наугад.

На R1–R3 можно работать вручную. Если используете ИИ как помощника, проверяйте его предложения и сохраняйте решение в том же документе и текущей ветке; отдельные AI-ветки и параллельные учебные задания не нужны. ИИ не принимает решение за владельца и не заменяет обязательные отметки по текущему diff.

## Отдельная передача R1 в реализацию

Она не заменяет продолжение R2/R3 и не входит в приёмку R1. Передайте разработчику фактические URL репозитория, ветку, полный SHA и путь `specification.md`:

```bash
git status --short --branch
git remote get-url origin
git branch --show-current
source_sha=$(git rev-parse HEAD)
git cat-file -e "$source_sha^{commit}"
git show "${source_sha}:specification.md"
```

Дерево должно быть чистым, а `show` — выводить принятую спецификацию. В корне отдельного checkout сервиса откройте [общий практикум разработчика](https://github.com/apolenkov/sdd-guide-credit-calculator-stage-3/blob/main/docs/developer-handoff.md) и выполните только начальную read-only проверку:

```bash
git status --short --branch
git rev-parse HEAD
sed -n '1,240p' docs/developer-handoff.md
```

Сообщение агенту:

```text
Прочитай docs/developer-handoff.md и AGENTS.md сервиса. Источник требований:
<URL репозитория>, <ветка>, <полный SHA>, путь specification.md.
Проверь доступность коммита и покажи specification.md из этого SHA.
Сопоставь требования с текущим состоянием, перечисли пробелы и предложи план
с проверками. Пока не меняй файлы или код, не создавай Change, не запускай
Apply и не называй read-only проверку реализацией новых функций.
```

Если SHA недоступен, дерево грязное или документ не совпадает с передачей, остановитесь. Переход к Change, Apply и коду требует отдельного разрешения.
